# HiMedia H10 mirroring profile

This profile was developed against `c8defdd70d7e6a04f4f1b71d353653682d594106`
(v0.0.31) on a HiMedia H10-G4 / Hi3798CV200 / Android 7 (API 24), using
the ARMv7 HiSilicon HEVC decoder and a TV connected at 1080p60.

## Reproduction and behavior

An iPhone screen-mirroring test with twelve brief flashes and short tones over
24 seconds initially produced a late tone, then only every other tone. Empty
audio RTP packets were discarded before sequencing, causing subsequent media
to stall behind apparently missing sequence numbers. With the silence fix and
audio timeline changes, all twelve tones were audible and approximately aligned
with the flashes in the tested configuration.

The device's `OMX.hisi.video.decoder.hevc` was available but excluded by the
existing HEVC selection policy when AVC could meet the requested size/rate.
The opt-in H10 profile admits that exact decoder only on H10-G4 / bigfish / API 24,
checks its requested size/rate, and disables HEVC software fallback for this
device so a failed hardware adaptation is visible. AVC fallback is retained.

The display60 profile keeps a persistent SurfaceView across preview/fullscreen
changes and can drain directly to it. It preserves the validated v2 startup and
surface behavior. A later experimental initial Surface handoff that introduced
late audio and incorrect aspect ratio is not included.

## Scope

- Native audio changes reset the decoder/queue/clock on RAOP FLUSH and actual
  discontinuities; a normal silence interval does not repeatedly reopen audio.
- PCM PTS, monotonic time and estimated OpenSL ES/mixer delay drive video timing;
  the GL fallback preserves presentation timestamps to its output buffers.
- Compressed audio packets are queued whole after bounded input retries;
  rejection returns the unused slot, output ranges are checked, and probe access
  is synchronized between input and drain threads.
- Chinese UI includes automatic system-language matching, an explicit language
  setting, persisted choices and localized notifications on Android 7+.
- Separate debug build types provide ARMv7 H10 profiles. `debug` and `release`
  have the H10/direct-surface flags disabled and do not receive H10 initial
  settings. Native audio and localization changes are shared and still require
  review/testing on other devices.

## Build and regression tests

Initialize the pinned submodules, then use JDK 21, Android SDK 36,
Build Tools 36.0.0, NDK 27.0.12077973 and CMake 3.22.1:

```bash
git submodule update --init --recursive
./gradlew assembleMvpH10Display60 --no-daemon --console=plain --max-workers=2
python3 tools/check-localization.py
bash tools/test-mvp.sh host
bash tools/test-mvp.sh arm
```

`tools/setup-wsl.sh` can prepare an Android toolchain in an environment with
write access to `/opt`. The Gradle CMake configuration applies the tracked
UxPlay patches to the pinned revision before building. Do not use
`git submodule update --remote` as a substitute for the pinned versions.

The APK is `app/build/outputs/apk/mvpH10Display60/app-mvpH10Display60.apk`,
with package `io.github.jqssun.airplay.mvph10display60`. The intermediate
`mvp`, `mvpHevc` (30 fps) and `mvpHevc60` variants are retained for comparisons.
Only one receiver should run at a time because the services share ports.
The profile uses a separate debug signature/package, and boot auto-start is
disabled initially. No signing keys, credentials or private deployment settings
are part of this contribution.

The tests cover audio input timeout/error/capacity cases, timeline and FLUSH,
normal silence versus PTS discontinuity, concurrent clock snapshots, empty RTP,
resend modes, duplicate packets and sequence wrap. The RAOP test uses an AES
stub; it exercises sequencing, not encryption. ARM executables can be copied
to an Android 7 ARMv7 device and run there. They do not measure speaker/display
synchronization.

## Tested configuration and measurement limits

Sender: iPhone 14 Pro Max; user-reported iOS version 26.6.2. Use Control Center
screen mirroring, not app-level video URL casting. The profile initializes a
2560x1440 maximum request, 60 fps maximum, fixed 40 ms audio cushion, low latency
and scheduled output-buffer release. This request does not change the TV's HDMI
mode or force the sender to send 60 fps.

Hardware HEVC was checked at all three levels: AirPlay selected HEVC, Android
started `OMX.hisi.video.decoder.hevc`, and `/proc/msp/omxvdec` reported H265.
Approximately 60 fps was observed at receive/decode stages in continuous
motion; the sender also dropped to 30 fps in some scenes. The user confirmed
audible tones aligned with flashes, normal video without dropped audio/stutter,
and acceptable mirroring latency for the retained v2 profile.

These observations **do not prove** a physical TV output of sixty distinct
frames every second or a precise end-to-end latency. HDMI refresh, receive,
decoder output, buffer release and physical presentation are separate metrics.
This Android 7 SurfaceFlinger returned unusable zero latency timestamps, and
render callbacks were incomplete. OpenSL ES playback timing is estimated and
does not account for all TV/amplifier processing delay. Other phones, codecs,
output routes and long-running sessions need additional validation.

## Existing upstream overlap

- UxPlay independently fixed the same empty-audio sequencing problem in
  [ec203121](https://github.com/FDH2/UxPlay/commit/ec203121355220dd90278a369eeabb0b8ba4f14a)
  on 2026-10-11. The Android project still pins an earlier UxPlay revision.
  Patch `0007` is the locally tested fix for that pinned revision, not a claim
  that current UxPlay remains unfixed. A future submodule upgrade could replace
  the overlapping part, but must reconcile the Android patches and tests.
- [PR #56](https://github.com/jqssun/android-airplay-server/pull/56) proposes a
  general `omx.hisi` whitelist for Kirin. This profile instead has a narrow
  H10 device gate and retains the normal policy elsewhere; the author may
  choose to consolidate the approaches.
- [PR #45](https://github.com/jqssun/android-airplay-server/pull/45) concerns AAC
  initialization and software fallback. The changes here address transient
  input pressure, whole-packet submission, output validation and synchronization,
  rather than adding an AAC software fallback.
